# パスワード再設定の運用設定

## 現在の設定状況（Resume_app）

- 保存・再表示で確認済み：Email OTP Expiration = 1200秒、最小8文字、英大文字・英小文字・数字を必須。
- URL確認済み：Site URL = `http://localhost:3000`、Redirect URLs = `http://localhost:3000/**`。開発環境の再設定画面は既存設定で許可済み。
- カスタムSMTPは無効。現在のFreeプランではSMTP未設定のままメールテンプレートを編集できず、Reset Passwordは既定のConfirmationURLのまま。
- 開発中は既定のメールとリンクで確認できる。共通クライアントがURLのフラグメントから認証状態を読み取り、画面はrecoveryセッションを使って更新する。件名・本文は英語の既定文となり、有効期限20分の独自文言は追加できない。
- 標準メールの宛先はSupabase組織のチームメンバーに限られ、送信上限は公式案内でプロジェクト全体2通/時（変更の可能性あり）。アプリに登録しただけのメールアドレスには送れない。
- 標準メールによる受信・再設定・再ログインは実操作で確認済み。独自メール本文はSMTP設定後に適用する。本番URLも公開先確定後に追加する。

## Supabaseで必須の設定

アプリのコードだけではメールの有効期限は変わらない。公開前に開発用・本番用の各Supabaseプロジェクトで設定する。

1. Authentication → Emailプロバイダーの `Email OTP Expiration` を **1200秒（20分）** にする。この設定は他のメールOTPにも影響する。
2. Authentication → URL ConfigurationでSite URLをアプリのURLにする。Redirect URLsに本番と開発環境の `/reset-password` のURLを追加する。
3. メール本文を独自化する場合は、カスタムSMTPを設定してから、Authentication → Emails → Templates → Reset Passwordを次のテンプレートに変更する。デフォルトの `ConfirmationURL` ではなく、`TokenHash` と `RedirectTo` を使用する。このカスタムリンクではフォーム送信時にrecoveryトークンを検証するため、ページを開くだけではトークンを消費しない。既定のConfirmationURLでは、Supabase側が先に検証し、戻り先でクライアントが認証状態を受け取る。両方の経路に対応している。

件名：パスワードの再設定

```html
<h2>パスワードの再設定</h2>
<p>以下のリンクから新しいパスワードを設定してください。</p>
<p><a href="{{ .RedirectTo }}?token_hash={{ .TokenHash }}&amp;type=recovery">パスワードを再設定する</a></p>
<p>リンクの有効期限は送信から20分です。使用済みのリンクは再利用できません。</p>
<p>このメールに心当たりがない場合は、何もする必要はありません。</p>
<p>Googleで登録した方は、Googleログインをご利用ください。</p>
```

4. 本番用SMTPが設定され、対象のメールアドレスに配送できることを確認する。
5. Supabase側のパスワードポリシーも、8文字以上・英大文字・英小文字・数字を必須に揃える。

通常のログインセッションを再設定の証拠として使わず、recoveryトークンを検証してから更新する。再設定セッションは共通のSupabaseクライアントが保持する。JWTの `amr.method = recovery` または `otp` でメールリンク認証を判別し、通常画面は再設定画面へ戻し、履歴書・AI使用回数などのAPIも署名検証後に拒否する。再設定・再送画面では通常のナビゲーションを表示しない。標準メールのimplicit flowでは再設定も `otp` として記録されるため、`recovery` のみで判定しない。新規登録確認も `otp` になるので、ログイン画面へのアクセスは許可し、通常のパスワード・Google認証への切り替えを妨げない。更新後は自動でローカルログアウトし、`/login?passwordReset=complete` に遷移して完了メッセージを表示する。Googleのみのidentityを持つアカウントでは、この画面からパスワードを追加しない。

## 受け入れ確認

- ログイン画面の導線からメール送信。未登録アドレスでも同じ完了案内になる。
- 実メールのリンクを別のブラウザーで開き、有効なパスワードで更新できる。
- 短いパスワード、大文字／小文字／数字の不足、確認欄の不一致で送信されない。
- 使用済みリンク、改ざんしたリンク、20分経過したリンクでは更新できず、再送に進める。
- 通常のログイン状態で `/reset-password` を直接開いても更新できない。
- GoogleのみのアカウントはGoogleログインに案内される。
- 更新後に自動ログアウトしてログイン画面へ遷移し、完了メッセージが表示される。新パスワードでは成功、旧パスワードでは失敗する。
- 再設定認証後に更新が失敗しても、同じセッションで更新を再試行できる。
- 再設定認証後に履歴書一覧・お問い合わせなどへ直接移動しても再設定画面へ戻される。再読み込みや別タブでも同じ制限が適用される。
- 再設定セッションのトークンで履歴書・AI使用回数APIを直接呼び出しても401となり、DB処理が実行されない。
- 通常のメール／パスワードログインとGoogleログインでは、従来どおり履歴書APIを利用できる。
- ログアウト失敗時は再設定画面に残り、更新を繰り返さずログアウトだけ再試行できる。
- メール送信・更新の通信失敗時に入力が残り、再試行できる。

参照：https://supabase.com/docs/guides/auth/auth-email-templates

この制限はアプリの画面と `getUserId` を通る独自APIが対象。Supabase Auth自体が発行するセッションを「パスワード変更専用」に変えるものではない。将来ブラウザーから直接DB・Storageへアクセスする場合は、RLSでもrecoveryセッションを制限する。
